# 发版说明怎么写：累计制

> 2026-09-15 起生效（大王定的）。改的是**发布页上那篇说明**的写法，不改版本号规则、不改产物、不改 updater。

## 一句话规则

**发布页不逐版罗列，而是把「上一个已发布版本之后」的所有版本合并成一篇。**

例：`0.4.4` 加了磁吸，`0.4.5` 修了磁吸的毛病 —— 发布页上不写两条，只写一句「增加磁吸」。
读者要知道的是"这一版比上次发布强在哪"，不是"中间改了几稿"。

## 为什么

逐版写有两个坏处：

1. **同一个功能被拆成好几条**，其中几条是"修上一条"的——读者读到"修复磁吸问题"时并不知道磁吸是什么时候加的。
2. **单版改动经常小到不成句**，比如"把 8px 改成 1px"。凑成一条读起来像凑数；并进它所属的那件事里才有意义。

## 谁写、写在哪

**唯一源头仍然是 `CHANGELOG.md`。** 只是当前版本那一段的**内容口径**变了：

- **本版段落 = 从上次发布到本版的累计摘要**（合并、去重、按事归类），不是"本版 diff"。
- 被并进来的旧版本段落**原样留着不动**——那是开发侧的完整履历，也是本版摘要的取材来源。
  `CHANGELOG.md` 因此同时是"开发履历（每版都在）"和"发布说明源头（只看最新那段）"。

合并是**编辑工作，要 AI 参与**：把同一件事的"加功能"与"后续修复"合成一句、把不成句的微调并进所属条目。
脚本不做这件事（机械去重会把两句话拼成一句半）。

## 怎么操作

```bash
# 1. 取材：把 (上一个已发布版本, 本版] 区间里所有版本的段落原样倒出来
node scripts/release-notes.js --since auto            # auto = 比本版小的最大 git tag
node scripts/release-notes.js 0.4.11 --since 0.4.9     # 也可以手写起点
#   → build/release-draft-0.4.11.md（不改写一个字，只是搬运 + 标出区间）

# 2. 把草稿合并成一篇，写回 CHANGELOG.md 的本版段落（## [0.4.11] - 日期）

# 3. 正经生成发布页说明（和以前完全一样，只认 CHANGELOG）
node scripts/release-notes.js 0.4.11
#   → build/release-notes-0.4.11.md = 本版段落正文 + docs/release-boilerplate.md 的固定尾巴
```

`--since auto` 认的是**本地 git tag**。本地 tag 少了会取错起点（比如只 fetch 过 `v0.4.6`，
就会把 `0.4.8` / `0.4.9` 也一起并进来）——**取材前先 `git fetch --tags`**，
或者直接手写 `--since <上一个已发布版本>`。

## 边界（别越界）

- **不合并旧版本段落本身。** 本版摘要覆盖旧版本，但旧版本段落留着。想清理履历是另一件事。
- **不改 `docs/release-boilerplate.md`** 的固定尾巴（安装 / 已知限制 / 许可证），那是每版都要说的，不参与合并。
- **不改产物格式、不改 updater 逻辑、不改版本号规则**（`package.json` 为准）。
- **技术细节该去哪**：发布页面向使用者，根因分析这类"为什么这么修"的深水区写进
  `docs/` 或 `HANDOVER.md`（§四 硬约束、§五 回归脚本），发布说明里只留结论和现象。
  发版自检（`scripts/post-release-check.js`）只比对**首行有内容的那句**，不会因为正文改写法而误报。

## 相关

- `CHANGELOG.md` 顶部有同样的说明（那份是给读者看的）。
- `scripts/lib/changelog-section.js` 提供区间取材（`changelogRange()` / `latestBelow()`）。
- `scripts/post-release-check.js` 第 ⑥ 项核对"发布页说明与 CHANGELOG 同源"。
